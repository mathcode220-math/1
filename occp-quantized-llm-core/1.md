## 3. الأخطاء التفصيلية للسبب الجذري

### 🔴 E-1 [الحرج الأول] — العدّاد لا يتقدم لحظة `layer_done` ⇒ الحلقة لا تنتهي أبداً

**الكود الحالي:**
```systemverilog
// increment يحدث داخل S_COMPUTE فقط:
if (state == S_COMPUTE) running_count <= running_count + 8'd1;
...
assign is_last_layer = (layer_count >= total_layers_reg) && started;
...
S_WAIT_DONE:  if (layer_done) next_state = S_LOOP_CHECK;
```

**آلية العطل:** عند التقاط `layer_done` في `S_WAIT_DONE` ينتقل `state` إلى `S_LOOP_CHECK`، لكن `running_count` لم يزد بعد الطبقة الأخيرة إلا إذا مررنا بدورة `S_COMPUTE` إضافية. في `S_LOOP_CHECK` لنموذج ثلاث طبقات يكون `layer_count = 2 < total_layers = 3` ⇒ `is_last_layer = 0` ⇒ الانتقال إلى `S_PREFETCH_W` بدلاً من `S_OUTPUT_TOKEN`.

**الدليل التجريبي (trace تشخيصي):**
```text
last loop-check: state=6 cnt=2 is_last=0    ← يجب أن يكون is_last=1
after edge:      state=2 cnt=2              ← PREFETCH بدل OUTPUT_TOKEN
```

**الأثر الوظيفي:** آلة الحالات تدور في `PREFETCH→COMPUTE→WAIT→LOOP` إلى ما لا نهاية، تحسب طبقة رابعة وهمية، ولا تُصدر توكناً أبداً. هذا عيب RTL حقيقي وسيُنتج silicon معطلاً لو نُقِل للتركيب.

**الإصلاح المقترح:** نقل الـ increment إلى لحظة اكتمال الطبقة:
```systemverilog
end else if ((state == S_WAIT_DONE) && layer_done) begin
    running_count <= running_count + 8'd1;
    started       <= 1'b1;
end
// ثم: is_last_layer = (running_count >= total_layers_reg) في LOOP_CHECK
```

### 🔴 E-2 — حالة `S_LOAD_LAYER_0` ميتة (Dead State) ومخالفة للعقد

المسار المتعاقد عليه (`contracts/recurrent_interfaces.yaml`):
`IDLE → LOAD_META → PREFETCH_W → LOAD_LAYER_0 → COMPUTE → WAIT_DONE → LOOP_CHECK`

لكن الكود:
```systemverilog
S_PREFETCH_W: if (weight_ready) next_state = S_COMPUTE;   // تخطّي LOAD_LAYER_0
```
`S_LOAD_LAYER_0 = 4'd3` معرّفة لكنها غير قابلة للوصول، ومخرجاتها المتعاقدة (`sel_external=1` لتحميل متجه الطبقة صفر الخارجي، و`weight_load_en` بشحن الطبقة التالية) مفقودة. **قرار مطلوب:** إما استعادتها في المخطط أو حذفها من العقد والحزمة — لا يجوز بقاء التناقض.

### 🔴 E-3 — تجاهل `softmax_done` في `S_WAIT_DONE` خلافاً للعقد

* العقد: `S_WAIT_DONE: if (layer_done && softmax_done) → S_LOOP_CHECK`
* الكود: `S_WAIT_DONE: if (layer_done) → S_LOOP_CHECK`

`softmax_done` تُستهلك فقط في `S_OUTPUT_TOKEN`. عند ربط softmax_core الحقيقي (P5) قد تبدأ الطبقة التالية قبل اكتمال تنشيط الطبقة الحالية — خطأ مزامنة كامن لا يظهر في الاختبار الحالي لأن الـ TB يقود الإشارات يدوياً.

### 🟠 E-4 — عدم توافق Icarus: اختيار بت ثابت داخل `always_comb`

السطر 141: `buf_sel = layer_count[0];` يُنتج تحذير `sorry: constant selects...` وقد يختلف سلوك المحاكاة عن التركيب. الإصلاح:
```systemverilog
wire buf_sel_w = layer_count[0];   // خارج always_comb
// أو: buf_sel = layer_count & 1'b1;
```

### 🟠 E-5 — خطر ضياع نبضة `output_token_valid` (Race على `softmax_done`)

`output_token_valid = (state == S_OUTPUT_TOKEN) && softmax_done` مشروطة بنفس الإشارة التي تُنهي الحالة. إذا وصلت `softmax_done` كنبضة أحادية الدورة متزامنة مع حافة Clock فقد تُلتقط للتtransition دون أن تستقر المخرجة للمراقب الخارجي. التوصية: قفل داخلي:
```systemverilog
always_ff @(posedge clk ...) if (state==S_OUTPUT_TOKEN && softmax_done) token_pulse <= 1;
```

### 🟡 E-6 — Testbench يفترض قفزة فورية `LOOP_CHECK → OUTPUT_TOKEN` في نفس الدورة

```systemverilog
expect_state("T6 loop-check", S_LOOP_CHECK);
expect_state("T6 output",     S_OUTPUT_TOKEN);   // "انتقال فوري" — غير صحيح في FSM مسجّلة
```
آلة حالات قياسية تنتقل حالة واحدة لكل حافة. حتى بعد إصلاح E-1 يحتاج T6/T8 إلى حافةclk إضافية بين الفحصين (أو دمج LOOP_CHECK منطقياً داخل WAIT_DONE وتوثيق ذلك في العقد).

### 🟡 E-7 — `started` لا تُصفَّر في مسارات الخروج الاستثنائي

تصفير `running_count/started` يحدث فقط عند `(S_IDLE && host_start)`. إذا أُضيفت مسارات `S_ERROR`/إلغاء لاحقاً يبقى `started=1` فيفسد `is_last_layer` في التوكن التالي. أخطاء T8 المرصودة هي أساساً تلويث حالة من فشل T6/T7 (E-1)، وليست دليلاً على عيب مستقل بعد.

## 4. فجوات معمارية ومهام غير منجزة

### 🔴 E-8 — ازدواجية تعريف الحالات (Package vs localparam)

`rtl/common/fsm_state_pkg.sv` يعرّف الحالات كحزمة، بينما `occp_pipeline_fsm.sv` يعيد تعريفها محلياً كـ `localparam` (بدافع توافق Icarus مع enums/packages). مصدرَا حقيقة قابلان للتباعد الصامت. الحل: إبقاء الحزمة مرجعاً + فحص تطابق تلقائي في TB أو CI.

### 🟡 E-9 — تعارض حجم رأس Metadata: 8 مقابل 9 بايت

* `contracts/metadata_format.yaml`: `header_size_bytes: 8`
* الخطة الأصلية لـ `metadata_writer.py`: `struct "<BI BH B"` = **9 بايت** مع `assert HEADER_SIZE == 9`

يجب حسم الاتجاه: اعتماد 8 بايت (مثلاً `total_layers:1 + layer_weight_bytes:3 + activation:1 + vector_len:2 + reserved:1`) وتعديل Python، أو تعديل العقد. كذلك `model_metadata_pkg.sv` بلا أي testbench لوحدة `metadata_parser.sv` ضمن `tb/`.

### 🔴 E-10 — ملفات Python الخاصة بالمرحلة P3 لم تُنشأ إطلاقاً

`software/metadata_writer.py` و`software/validate_bin.py` **غير موجودين**، وبالتالي `compiler.py --emit-header` غير منفذة، ولا توجد وسيلة لإنتاج ملف `.bin` برأس metadata لاختبار التكامل.

### 🔴 E-11 — المرحلة P4 غير منفذة: لا يوجد `occp_top_recurrent.sv`

`rtl/top/` يحتوي فقط `recurrent_datapath.sv`. لا تكامل شامل (FSM + datapath + pingpong + sa_done_generator) ولا `tb_occp_top_recurrent.sv`. غياب التكامل هو سبب عدم اكتشاف E-1 مبكراً — حلقة لا نهائية كانت ستظهر فوراً في اختبار توكن كامل.

### 🟡 E-12 — `sa_done_generator` غير موصولة بأي مسار حقيقي

اجتازت اختبارها الذاتي، لكن `layer_done` في `recurrent_datapath` يولده عدّاد داخلي ثابت (`LAYER_LATENCY=3`) وليس الوحدة القابلة للبرمجة. الربط من metadata→latency_cfg مؤجل.

### 🟡 E-13 — `weight_pingpong`: خرج `dma_addr` و`load_done` بدون محرك DMA مكتمل

الواجهة موجودة واختبارها ناجح، لكن الشحن في TB يدوي؛ في التكامل يجب توصيل `weight_ready = load_done` وتشغيل عدّاد DMA ذاتي أثناء `S_PREFETCH_W`.
